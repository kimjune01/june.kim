**Title:** Audit notes: a tag-pinned grader, out-of-tree verification, and no conflicts statement

---

I audited DeepSWE v1 and v1.1 earlier this year ([auditing-deepswe](https://june.kim/auditing-deepswe), [auditing-deepswe-v1-1](https://june.kim/auditing-deepswe-v1-1)). This suite builds 20 of its 27 tasks on that corpus, so I ran the same shipped-artifact checks here. Several clear cleanly, and they go first, because a check that can't exonerate can't convict.

- The receipt bundle is retrievable: under each run directory, `metadata/contracts/` carries `git-diff.patch`, `harness-report.json` with the reward, and the round logs. `results/debug/report-deepswe-v1.1-gpt56-sol-codex-cli-high-r01/langchain-request-coalescing/codex-cli-high/langchain-request-coalescing-codex-cli-high-run-01/metadata/contracts/harness-report.json` records `"status": "fail"`, `"score": {"passed": 0, "total": 1}`, the reproducible-verdict bundle DeepSWE's own artifacts don't ship.
- The exclusion ledger is complete: `assets/model-run-statistics/excluded-runs.csv` names both over-90-round Tura Balanced runs with their reasons, matching the 280/278 split in the doc.
- The methodology pre-concedes the reading-level issues an auditor would otherwise raise for free: band-edge selection bias (§9.3), sparse-pool distortion (§9.2), CI dependence under clustering (§8.4, §10.6), and contamination on the public rewrite sources (§10.4).

Recommendations.

1. *The grader should be commit-addressed.* Every DeepSWE `harness.json` and `harness-report.json` records the grader at `datacurve-ai/deep-swe`, `commit: "v1.1"` (e.g. `results/debug/report-deepswe-v1.1-gpt56-sol-codex-cli-high-r01/langchain-request-coalescing/harness.json`, under `scoreItems[0].harnessCodeLocation`). A tag floats, and the upstream v1.1 leaderboard is live rather than frozen; §7.1 pins task identity to a base commit, but the same discipline isn't applied to the verifier. It bites here specifically: `narwhals-rolling-window-suite` and `langchain-request-coalescing`, two tasks in `canonical_tasks.json`, were among four DeepSWE golds I found failing their own verifiers in v1, and both were re-graded before v1.1. A run recorded against the tag `v1.1` can't say which re-grade scored it. Pin the upstream commit SHA and the verifier image digest.
2. *The reward should re-derive from the published artifacts.* The receipt shows Tura's patch and the recorded reward, but the grader itself (`grader.py`, `test.patch`, the fail-to-pass/pass-to-pass node IDs) lives out-of-tree in DeepSWE, where those hidden tests aren't published, a gap my v1.1 audit documented upstream. So a reader can inspect a verdict but can't reproduce it from either repo. Vendor the pinned grader and test fixtures where licensing allows; the node-ID set alone names the tests without supplying them.
3. *The harness should guard off-task state.* I don't see a step that manifests the workspace at agent handoff and diffs off-task state against it, in either the methodology or the shipped `harness-report.json` schema. If it isn't in the harness source either, a run that completes a rewrite/HTML task while damaging unrelated state still scores, since those tasks grade final browser/backend/db state. Worth confirming from the harness code.
4. *Each rewrite harness should pass its own reference build.* The rewrite tasks ship no reference implementation run through their own harness, so it's unstated whether the 52/48/55/18/63 assertions are jointly satisfiable by a known-good build. One reference run per rewrite harness settles it cheaply.
5. *The methodology should disclose the conflict of interest.* `tura-balanced` and `tura-direct` are this project's own runtime configurations, benchmarked here against Codex. Read as marketing, that's unremarkable. Read as measurement, which is how the methodology asks to be read, it's a disclosure the reader needs to weight the result. Nothing in the README or the four docs states it. It costs a sentence and breaks no comparability.

Every claim above cites its artifact path and is checkable from the repo, without privileged access or a model run.
